# 《Local AI 隐私实践入门：什么时候数据真的没有离开你的设备？》

> **Status: Proposed outline / research required**  
> 本文件只定义教程结构和研究问题，不提供未经核验的技术结论，也不构成安全保证。

## 目标读者

对 AI 工具有基础使用经验，但不是隐私、网络或系统安全专家的华语 Builder。

## 教程目标

帮助读者建立一个可操作的数据流检查框架：不要只根据产品名称或“Local”标签判断隐私，而是识别输入、模型、网络请求、存储、Telemetry、更新和扩展分别可能把数据带到哪里。

教程需要同时说明 Local AI 的潜在隐私优势、现实限制和使用成本，不把“本地运行”等同于“完全离线”或“绝对安全”。

## 1. Local AI 为什么和 Privacy 有关系

计划说明：

- 推理发生位置为什么会影响数据暴露面；
- 数据控制、保留期限、访问主体和可删除性是不同问题；
- Privacy、Security、Anonymity 和 Confidentiality 不能互相替代。

研究问题：

- 本教程采用什么最小 Threat Model？
- “数据离开设备”具体包括哪些数据：Prompt、文件、Embedding、日志、设备信息还是使用指标？
- 哪些隐私收益来自本地推理，哪些取决于操作系统、应用和配置？

## 2. Local model 与 Cloud API 的数据路径区别

计划产出两张来源明确的简化数据流图：

```text
User input → Local application → Local model runtime → Local output
```

```text
User input → Client application → Network → API provider → Model service → Response
```

研究问题：

- 两种路径各自可能出现哪些日志、缓存、临时文件和第三方组件？
- Cloud API 的数据保留和训练使用规则应从哪些官方文件核验？
- Local runtime 是否会调用远程服务，如何从工具文档和实际测试交叉验证？

## 3. “本地运行”并不一定意味着完全不联网

计划检查以下可能的联网行为，而不是预设它们一定存在：

- 首次安装和模型下载；
- 版本与安全更新；
- Telemetry、Analytics 和 Crash Reports；
- 登录、License 或账户验证；
- Web Search、插件、外部 Tool Calling；
- 远程 Embedding、Reranking、Storage 或同步服务。

研究问题：

- 哪些请求是核心功能必需，哪些可以关闭？
- 关闭后会损失什么功能或安全更新？
- UI 设置、隐私政策和实际网络行为是否一致？

## 4. 常见 Local AI 工具的基础架构

不先做工具排名。选择少量代表性架构进行说明：

- Desktop application + bundled/local runtime；
- Local model server + browser/client；
- Command-line runtime；
- Local RAG application；
- Hybrid application with optional cloud features。

研究问题：

- 每类架构的信任边界在哪里？
- 模型文件、对话记录、Embedding 和索引默认存在哪里？
- 哪些组件是 Open Source，哪些只是提供本地运行能力？
- 如何确认具体版本和默认配置？

## 5. 如何检查应用是否存在外部请求

计划设计一个面向普通 Builder 的分层检查流程：

1. 阅读官方架构、隐私政策和 Telemetry 文档；
2. 记录测试版本、操作系统、安装来源和配置；
3. 在没有敏感数据的测试环境中建立基线；
4. 使用操作系统或网络观察工具记录域名、目标地址和请求时间；
5. 分别测试启动、模型下载、对话、文件导入、更新和退出等动作；
6. 区分“观察到连接”与“已证明传输了某类内容”；
7. 记录无法解释的请求和测试限制。

研究问题：

- macOS、Windows 和 Linux 分别选择哪些可复现、低门槛工具？
- 是否需要区分 DNS、TCP/TLS 连接与可读取的 HTTP 内容？
- HTTPS 加密条件下，普通用户能可靠观察到什么，不能证明什么？
- 如何避免抓取真实私人数据或违反服务条款？

## 6. 需要检查的数据流

教程将使用统一清单记录：

| Data / component | 需要查明的问题 |
|---|---|
| Prompt 与输入文件 | 在哪里处理、缓存和保存？ |
| Model weights | 从哪里下载，如何验证来源和完整性？ |
| Embeddings / vector store | 在本地还是远程生成与保存？ |
| Conversation history | 默认路径、保留时间、删除方式是什么？ |
| Telemetry / analytics | 默认是否开启，发送哪些类别的数据？ |
| Crash reports / logs | 是否可能包含 Prompt、路径或系统信息？ |
| Updates | 向哪里检查更新，关闭后的 Trade-off 是什么？ |
| Plugins / web tools | 哪些输入会被传给第三方？ |

研究问题：每一个结论能否同时得到官方文档、源代码或可复现实测中的至少一种支持？高风险结论是否需要两类证据交叉核验？

## 7. 普通 Builder 可以采取的基础实践

这一部分将在来源核验后形成具体步骤，候选内容包括：

- 在使用前画出最小数据流和信任边界；
- 使用测试数据验证配置和联网行为；
- 检查 Telemetry、同步、插件与远程服务设置；
- 记录工具版本、模型来源和更新策略；
- 对高敏感任务采用单独环境、最小权限和必要的网络控制；
- 定期复查更新是否改变默认行为。

研究问题：每项实践的适用前提、失败方式和可用性成本是什么？哪些建议对非专家而言可能造成错误安全感？

## 8. Trade-offs

计划讨论：

- Privacy 与设备性能、能耗、延迟和模型能力；
- 离线控制与及时安全更新；
- 自托管控制与维护责任；
- Open Source 可审计性与实际完成审计之间的差距；
- 易用性与配置透明度。

不把任何一种架构描述为普遍最优。

## 9. Limitations

必须明确：

- 网络观察不能自动证明请求中包含或不包含某类数据；
- 没有观察到请求，不等于系统在所有条件下都不会联网；
- 应用更新、模型版本、插件和操作系统可能改变行为；
- 本教程不能替代专业安全审计、法律意见或组织合规评估；
- Local AI 仍可能受到恶意软件、错误权限、日志泄露、物理访问和供应链风险影响；
- 结论必须限定到实际测试的版本、平台和配置。

## 10. Further Reading 与来源标准

正式版本只使用能够追溯的来源，并在每条关键技术事实附近标注：

- 工具官方文档、架构说明、隐私政策和 Telemetry 文档；
- 对应版本的源代码、Release Notes 或配置说明；
- 操作系统官方网络与隐私文档；
- 原始安全研究、技术标准或同行评审论文；
- 可复现的测试步骤和测试日期。

第三方博客可以用于发现线索，但不能单独支撑关键安全或隐私结论。
